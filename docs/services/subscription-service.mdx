# Subscription Service

## 1. Amaç

`subscription-service`, TheFoodHero ekosisteminde abonelik planlarını, abonelik durumlarını, plan geçişlerini, deneme süresini, abonelik temelli kullanım haklarını ve servisler arası abonelik kontrolünü yöneten domain servisidir.

- Diyetisyen veya klinik bazlı abonelik yönetimi
- Free / Trial / Basic / Pro / Clinic gibi planların yönetimi
- Abonelik yaşam döngüsü takibi
- Trial başlatma ve sonlandırma
- Plan yükseltme, plan düşürme ve iptal süreçleri
- App-service içindeki feature tanımlarına referanslı subscription entitlement yönetimi
- AI, SMS, danışan, randevu, store ve benzeri kullanımlar için quota/usage yönetimi
- Payment-service ile subscription ödeme akışının koordinasyonu
- Diğer servislere subscription summary, feature access ve limit kontrolü sağlama
- Event-driven mimariyle abonelik durum değişikliklerinin yayılması



## 2. Servisin sorumlulukları

`subscription-service` aşağıdaki işlerden sorumludur:

- Plan oluşturma ve yönetme
- Plan fiyat referanslarını tutma
- Abonelik oluşturma
- Trial subscription başlatma
- Abonelik state yönetimi
- Plan değişikliklerini yönetme
- Dönem sonunda downgrade işlemi planlama
- Abonelik iptali
- Abonelik askıya alma / yeniden aktif etme
- Subscription entitlement snapshot oluşturma
- Feature referansları üzerinden plan haklarını yönetme
- Usage counter tutma
- Usage limit kontrolü
- Servisler arası `check-feature`, `check-limit`, `increment-usage` endpointleri sağlama
- Subscription event publish etme
- Payment-service eventlerini consume ederek abonelik state güncelleme

## 9. Veritabanı Tasarımı

### 9.1 Plan

Plan şablonlarını tutar.

```prisma
model Plan {
  id          String   @id @default(cuid())
  code        String   @unique
  name        String
  description String?
  isActive    Boolean  @default(true)
  sortOrder   Int      @default(0)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  prices       PlanPrice[]
  entitlements PlanEntitlement[]
  subscriptions Subscription[]

  @@map("Plan")
}
```

Örnek planlar:

```text
FREE
TRIAL
BASIC
PRO
CLINIC
ENTERPRISE
```

Plan doğrudan abonelik değildir. Plan sadece abonelik oluşturulurken kullanılan ticari şablondur.



### 9.2 PlanPrice

Plan fiyat bilgisini tutar. Gerçek tahsilat payment-service tarafından yapılır.

Bu tablo payment işlemi yapmaz, sadece subscription planının fiyatını ve payment-service’e gönderilecek tutarı belirlemek için kullanılır.

```prisma
model PlanPrice {
  id            String        @id @default(cuid())
  planId        String
  billingPeriod BillingPeriod
  currency      String        @default("TRY")
  amount        Decimal       @db.Decimal(18, 2)
  taxRate       Decimal       @default(0) @db.Decimal(5, 2)
  isActive      Boolean       @default(true)

  paymentProductRef String?
  paymentPriceRef   String?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  plan Plan @relation(fields: [planId], references: [id])

  @@index([planId])
  @@unique([planId, billingPeriod, currency, isActive])
  @@map("PlanPrice")
}
```

`paymentProductRef` ve `paymentPriceRef`, payment-service tarafında bir ürün/fiyat karşılığı tanımlanırsa referans olarak kullanılabilir.

Bu alanlar provider referansı değil, payment-service referansıdır.



### 9.3 SubscriptionFeatureRef

App-service içindeki feature tanımlarının subscription-service projection karşılığıdır.

```prisma
model SubscriptionFeatureRef {
  id String @id @default(cuid())

  appFeatureId String?
  featureKey   String @unique
  name         String
  description  String?
  valueType    SubscriptionFeatureValueType

  sourceService String @default("app-service")
  isActive      Boolean @default(true)
  syncedAt      DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  entitlements PlanEntitlement[]

  @@index([appFeatureId])
  @@index([featureKey])
  @@index([isActive])
  @@map("SubscriptionFeatureRef")
}
```

App-service feature güncellendiğinde event yayınlar:

```text
app.feature.created
app.feature.updated
app.feature.disabled
```

Subscription-service bu eventleri consume ederek `SubscriptionFeatureRef` tablosunu günceller.



### 9.4 PlanEntitlement

Planın hangi feature’ı hangi limitlerle sunduğunu belirtir.

```prisma
model PlanEntitlement {
  id        String @id @default(cuid())
  planId    String
  featureId String

  isEnabled  Boolean @default(true)
  limitValue Decimal? @db.Decimal(18, 4)
  period     EntitlementPeriod @default(NONE)
  metadata   Json?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  plan    Plan @relation(fields: [planId], references: [id])
  feature SubscriptionFeatureRef @relation(fields: [featureId], references: [id])

  @@unique([planId, featureId])
  @@index([planId])
  @@index([featureId])
  @@map("PlanEntitlement")

```

Örnek:

```text
PRO -> ai.menu_generate.monthly_count -> enabled -> 100 -> MONTHLY
BASIC -> video_call.enabled -> false -> NONE
CLINIC -> staff.max_count -> enabled -> 10 -> NONE
```

### 9.5 BillingProfileRef

Fatura kesme ve finansal bilgi payment-service tarafında tutulur. Subscription-service sadece aboneliğin hangi tenant/user/clinic adına yürüdüğünü bilmelidir.

Bu tablo fatura adresi, vergi numarası veya ödeme yöntemi tutmaz.
Bu bilgiler payment-service domain’indedir.
Buradaki amaç sadece subscription bağlamını temsil etmektir.

### 9.6 Subscription

Abonelik lifecycle merkez modelidir.

```prisma
model Subscription {
  id String @id @default(cuid())

  tenantId String
  ownerUserId String
  clinicId String?

  billingProfileRefId String
  planId String

  status SubscriptionStatus
  billingPeriod BillingPeriod

  currentPeriodStart DateTime?
  currentPeriodEnd   DateTime?

  trialStart DateTime?
  trialEnd   DateTime?

  cancelAtPeriodEnd Boolean @default(false)
  canceledAt        DateTime?
  suspendedAt       DateTime?
  expiredAt         DateTime?

  activationPaymentRefId String?
  latestPaymentRefId     String?

  planSnapshot        Json?
  entitlementSnapshot Json?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  billingProfileRef BillingProfileRef @relation(fields: [billingProfileRefId], references: [id])
  plan              Plan              @relation(fields: [planId], references: [id])

  usageCounters SubscriptionUsageCounter[]
  paymentRefs   SubscriptionPaymentRef[]
  scheduledChanges SubscriptionScheduledChange[]

  @@index([tenantId])
  @@index([ownerUserId])
  @@index([clinicId])
  @@index([status])
  @@index([currentPeriodEnd])
  @@map("Subscription")
}
```

#### Önemli alanlar

#### `planSnapshot`

Abonelik oluşturulduğu anda planın ticari snapshot bilgisini tutar.

Örnek:

```json
{
  "planCode": "PRO",
  "planName": "Professional",
  "billingPeriod": "MONTHLY",
  "amount": 499.00,
  "currency": "TRY"
}
```

#### `entitlementSnapshot`

Abonelik başladığı anda plan haklarını snapshot olarak tutar.

Örnek:

```json
{
  "client.max_count": {
    "enabled": true,
    "limitValue": 100,
    "period": "NONE"
  },
  "ai.menu_generate.monthly_count": {
    "enabled": true,
    "limitValue": 100,
    "period": "MONTHLY"
  }
}
```

Bu snapshot, plan sonradan değişse bile mevcut aboneliğin hangi koşullarla başladığını izlemeyi sağlar.

#### PaymentRef ne işe yarar?

Bu model payment-service’in yerini almaz.

Sadece şu sorulara subscription-service içinde cevap verebilmek için kullanılır:

```text

Plan değişikliği için ödeme bekleniyor mu?
Başarısız ödeme sonrası subscription PAST_DUE mu?
```

## 12. İş Akışları

### 12.1 Yeni Diyetisyen Kaydı Sonrası Trial Başlatma

```text
1. user-service dietisyen hesabı oluşturur.
2. user-service user.created eventi yayınlar.
3. subscription-service eventi dinler.
4. tenantId + ownerUserId için BillingProfileRef oluşturur.
5. TRIAL plan bulunur.
6. Subscription kaydı TRIALING olarak oluşturulur.
7. Trial period set edilir.
8. Plan entitlement snapshot oluşturulur.
9. subscription.trial.started eventi yayınlanır.
```

Bu akışta payment-service çağrısı yapılmaz.



### 12.2 Ücretli Plan Satın Alma

```text
1. Kullanıcı BASIC / PRO / CLINIC plan seçer.
2. Frontend subscription-service /checkout endpointine istek atar.
3. subscription-service DRAFT veya PAYMENT_PENDING subscription oluşturur.
4. planSnapshot ve entitlementSnapshot hazırlanır.
5. subscription-service payment-service'e ödeme order oluşturma isteği gönderir.
6. payment-service ödeme sürecini başlatır.
7. subscription-service SubscriptionPaymentRef kaydı oluşturur.
8. Frontend ödeme URL veya 3DS yönlendirme bilgisini alır.
9. payment-service ödeme sonucunu event olarak yayınlar.
10. subscription-service payment eventini consume eder.
11. Başarılı ödeme sonrası subscription ACTIVE yapılır.
```

### 12.3 Payment Succeeded Event Consume

```text
1. payment.transaction.succeeded eventi alınır.
2. relatedEntityType = SUBSCRIPTION kontrol edilir.
3. relatedEntityId ile subscription bulunur.
4. SubscriptionPaymentRef SUCCEEDED yapılır.
5. Subscription status ACTIVE yapılır.
6. currentPeriodStart ve currentPeriodEnd set edilir.
7. subscription.activated eventi yayınlanır.
8. Redis cache temizlenir.
```

### 12.4 Payment Failed Event Consume

```text
1. payment.transaction.failed eventi alınır.
2. relatedEntityType = SUBSCRIPTION kontrol edilir.
3. SubscriptionPaymentRef FAILED yapılır.
4. Yeni satın alma ise subscription PAYMENT_FAILED yapılır.
5. Yenileme ise subscription PAST_DUE yapılır.
6. Grace period başlatılır.
7. subscription.payment_failed eventi yayınlanır.
8. notify-service için bildirim eventi publish edilir.
```



### 12.5 Plan Yükseltme

```text
1. Kullanıcı BASIC -> PRO geçmek ister.
2. subscription-service mevcut subscription'ı bulur.
3. Yeni plan ve fiyat bulunur.
4. Fiyat farkı veya yeni dönem ücreti hesaplanır.
5. payment-service'e PLAN_UPGRADE reason ile ödeme order isteği gönderilir.
6. SubscriptionPaymentRef PENDING oluşturulur.
7. payment-service success eventi gönderirse plan güncellenir.
8. entitlementSnapshot yenilenir.
9. subscription.plan_changed eventi yayınlanır.
```

Plan yükseltme genellikle anında uygulanabilir.


### 12.6 Plan Düşürme

MVP için önerilen yaklaşım: dönem sonunda düşürme.

```text
1. Kullanıcı PRO -> BASIC geçmek ister.
2. SubscriptionScheduledChange oluşturulur.
3. Mevcut plan currentPeriodEnd tarihine kadar devam eder.
4. Dönem sonunda scheduler pending change'i uygular.
5. subscription.plan_changed eventi yayınlanır.
```

Bu akışta ödeme alınmayabilir. Gerekirse yeni dönem yenilemesinde payment-service devreye girer.


### 12.7 Abonelik İptali

```text
1. Kullanıcı aboneliği iptal eder.
2. cancelAtPeriodEnd = true yapılır.
3. SubscriptionScheduledChange CANCEL_AT_PERIOD_END oluşturulur.
4. Kullanıcı currentPeriodEnd tarihine kadar aktif kullanır.
5. Dönem sonunda subscription CANCELED veya EXPIRED yapılır.
6. subscription.canceled eventi yayınlanır.
```

### 12.8 Renew / Yenileme Akışı

```text
1. Scheduler currentPeriodEnd yaklaşan abonelikleri bulur.
2. subscription-service payment-service'e RENEWAL reason ile payment order oluşturma isteği gönderir.
3. payment-service tahsilat sürecini yönetir.
4. payment succeeded event gelirse currentPeriodStart/currentPeriodEnd yenilenir.
5. payment failed event gelirse subscription PAST_DUE olur.
6. Grace period sonunda ödeme yoksa SUSPENDED veya EXPIRED yapılır.
```

## 13. Feature ve Limit Kontrol Akışı

### 13.1 Check Feature

```text
1. Servis subscription-service'e tenantId + featureKey ile istek atar.
2. Aktif subscription bulunur.
3. entitlementSnapshot veya PlanEntitlement üzerinden feature bulunur.
4. isEnabled kontrol edilir.
5. Boolean response döner.
```

Örnek request:

```json
{
  "tenantId": "tenant-id",
  "featureKey": "video_call.enabled"
}
```

Örnek response:

```json
{
  "allowed": true,
  "featureKey": "video_call.enabled",
  "source": "SUBSCRIPTION"
}
```

### 13.2 Check Limit

```text
1. Servis tenantId + featureKey ile limit kontrolü ister.
2. Aktif subscription bulunur.
3. Entitlement limit değeri alınır.
4. Dönemsel usage counter bulunur.
5. remaining hesaplanır.
6. allowed bilgisi döner.
```

Örnek response:

```json
{
  "allowed": true,
  "featureKey": "ai.menu_generate.monthly_count",
  "limit": 100,
  "used": 25,
  "remaining": 75,
  "periodEnd": "2026-06-30T23:59:59.000Z"
}
```

### 13.3 Increment Usage

```text
1. Servis başarılı işlem sonrası usage artırma isteği gönderir.
2. subscription-service ilgili period counter'ı bulur veya oluşturur.
3. Transaction içinde usedValue artırılır.
4. Limit aşımı varsa hata döner veya soft limit event publish edilir.
```

### 13.4 Reserve / Commit Usage

AI token kullanımı gibi tahmini kullanım senaryolarında önerilir.

```text
1. ai-service ReserveUsage çağırır.
2. subscription-service limit kontrolü yapar ve rezervasyon oluşturur.
3. AI işlemi tamamlanır.
4. ai-service CommitUsage çağırır.
5. Gerçek token değeri usage counter'a işlenir.
6. Hata olursa ReleaseUsage çağrılır.
```

## 16. Cache Stratejisi

Subscription kontrolü sık yapılacağı için Redis cache kullanılmalıdır.

Önerilen key yapısı:

```text
subscription:summary:{tenantId}
subscription:entitlements:{tenantId}
subscription:usage:{tenantId}:{featureKey}:{period}
subscription:feature-ref:{featureKey}
```

TTL önerisi:

```text
summary: 5-15 dakika
entitlements: 5-15 dakika
usage: 1-5 dakika
feature-ref: 15-60 dakika
```

Cache invalidation:

- subscription activated
- subscription plan changed
- subscription canceled
- subscription suspended
- entitlement changed
- app feature updated
- usage increment
- payment succeeded / failed event consumed



## 17. Transaction ve Idempotency

Transaction içinde yapılması gereken işlemler:

- Subscription oluşturma
- SubscriptionPaymentRef oluşturma
- Payment succeeded event consume
- Payment failed event consume
- Plan change apply
- Scheduled change apply
- Usage increment
- Usage reservation commit/release
- Subscription cancel
- Subscription suspend/reactivate

Idempotency kuralları:

- Checkout için `subscriptionId + planId + billingPeriod + period` bazlı idempotency key kullanılmalıdır.
- Payment event consume edilirken `eventId` veya `paymentTransactionId` tekrar işlenmemelidir.
- Aynı subscription için aynı anda birden fazla aktif plan change olmamalıdır.
- Usage increment için gerekirse caller idempotency key kabul edilmelidir.

## 18. Diğer Servislerle Entegrasyon

### 18.1 auth-service

Auth-service kimlik doğrulama ve token üretiminden sorumludur.
Subscription-service auth-service tablosuna FK vermez.
JWT içine subscription summary eklenebilir:

```json
{
  "tenantId": "tenant-id",
  "subscriptionPlan": "PRO",
  "subscriptionStatus": "ACTIVE"
}
```

Ancak kritik kontrollerde subscription-service kaynak kabul edilmelidir.


### 18.2 user-service

User-service tenant, clinic, user ve role bilgisinin sahibidir.

Subscription-service bu servisle şu ID’ler üzerinden ilişki kurar:

```text
tenantId
ownerUserId
clinicId
```

User/tenant oluşturulduğunda trial abonelik başlatılabilir.

### 18.3 app-service

App-service feature katalog ve feature flag/config bilgisinin sahibidir.
Subscription-service app-service’den feature referanslarını alır ve `SubscriptionFeatureRef` içinde projection olarak tutar.
Subscription-service feature flag yönetmez.

### 18.4 payment-service

Payment-service ödeme ve fatura domain’inin sahibidir.
Subscription-service ödeme başlatmak için payment-service çağırır.
Payment sonucu event üzerinden subscription-service’e yansır.
Subscription-service invoice, transaction, refund veya card token tutmaz.

### 18.5 appointment-service

Appointment-service randevu oluşturmadan önce limit kontrolü yapar:

```text
check-feature: appointment.enabled
check-limit: appointment.monthly_count
increment-usage: appointment.monthly_count
```

### 18.6 chat-service

Chat-service chat ve video görüşme için kontrol yapar:

```text
check-feature: chat.enabled
check-feature: video_call.enabled
check-limit: chat.monthly_message_count
```

### 18.7 ai-service

AI-service maliyetli işlemler için subscription-service’i kullanır:

```text
check-limit: ai.token.monthly_count
reserve-usage: ai.token.monthly_count
commit-usage: ai.token.monthly_count
```

### 18.8 notify-service

Notify-service SMS gibi ücretli bildirimlerde limit kontrolü yapabilir:

```text
check-limit: notification.sms.monthly_count
increment-usage: notification.sms.monthly_count
```

### 18.9 store-service

Store-service store modülü ve ürün limiti için kontrol yapar:

```text
check-feature: store.enabled
check-limit: store.product.max_count
```
