# App Service

## 1. Amaç

`app-service`, TheFoodHero ekosisteminde uygulama konfigürasyonlarını, uygulama menülerini, feature flag yönetimini, kullanıcı geri bildirimlerini, bilgi talep formlarını ve sistem entegrasyon tanımlarını yöneten merkezi destek servisidir.

Bu servis doğrudan kullanıcı kimlik doğrulama, abonelik, randevu, chat, diyet planı veya ödeme işlemlerinin domain mantığını yönetmez. Bunun yerine diğer servislerin ve frontend uygulamalarının ihtiyaç duyduğu uygulama seviyesindeki yapılandırmaları merkezi olarak sağlar.

`app-service` özellikle şu ihtiyaçları karşılar:

* Web, mobil, admin panel, API, mikroservis ve worker uygulamalarının merkezi kaydı
* Ortam bazlı uygulama ayarları yönetimi
* Rol bazlı ve uygulama bazlı dinamik menü yönetimi
* Feature flag ile özelliklerin kontrollü açılıp kapatılması
* Kullanıcı feedback ve hata bildirimi kayıtlarının toplanması
* Landing page veya tanıtım sayfası üzerinden bilgi talebi yönetimi
* SMS, email, ödeme, harita, storage, AI ve webhook entegrasyonlarının merkezi tanımlanması
* Servislerin aktif provider/entegrasyon bilgisini app-service üzerinden okuyabilmesi
* Uygulama versiyon, base URL ve ortam bilgilerinin merkezi yönetimi
* Event-driven mimariyle konfigürasyon değişikliklerinin diğer servislere yayılması

---

## 2. Servisin Sorumlulukları

`app-service` aşağıdaki sorumluluklara sahip olmalıdır:

* Uygulama kayıtlarını yönetmek
* Uygulama ortam ayarlarını yönetmek
* Uygulama versiyon bilgisini tutmak
* Menü yapılarını tanımlamak
* Menüleri role göre filtrelemek
* Menülerin sıralamasını ve parent-child yapısını yönetmek
* Feature flag tanımlarını yönetmek
* Feature flag değerlerini environment bazlı sunmak
* Kullanıcı feedback kayıtlarını almak
* Feedback durumlarını yönetmek
* Bilgi talebi formlarını kaydetmek
* Entegrasyon sağlayıcılarını tanımlamak
* Varsayılan entegrasyon sağlayıcısını seçmek
* Entegrasyon sağlık/hata durumlarını takip etmek
* Hassas entegrasyon bilgilerinin secret referanslarını yönetmek
* Diğer servisler için internal config lookup endpointleri sağlamak
* Konfigürasyon değişikliklerinde event publish etmek
* Sık okunan config verileri için cache stratejisi sağlamak

## 3. Servisin TheFoodHero Mimarisindeki Konumu

TheFoodHero mikroservis mimarisinde `app-service`, core business servislerinden ziyade platform configuration servisi olarak konumlanmalıdır.

Genel mimari konum:

```text
Frontend / Mobile / Admin
        |
        v
API Gateway / Nginx
        |
        v
app-service
        |
        +--> PostgreSQL app-service database
        +--> Redis cache
        +--> Redis Streams event publish
        +--> Secret Manager / encrypted data lookup
```

Diğer servislerle ilişki:

```text
auth-service          -> app-service: app settings / admin menu
user-service          -> app-service: user feedback reference
subscription-service  -> app-service: payment integration lookup
notify-service        -> app-service: email / SMS integration lookup
ai-service            -> app-service: AI provider config lookup
geo-service           -> app-service: map provider config lookup
store-service         -> app-service: payment / storage integration lookup
web/mobile/admin      -> app-service: menu, feature flag, app settings, feedback
```

## 4. Diğer Servislerle Entegrasyon

### 4.1 auth-service

`auth-service`, kullanıcı kimlik doğrulama, access token, refresh token ve internal token üretiminden sorumludur.

App-service auth-service’den kullanıcı doğrulaması yapmaz. Gelen request’lerde auth middleware tarafından doğrulanmış user context veya internal service context kullanılır.

Kullanım örnekleri:

* Admin panel menülerini role göre döndürmek
* Login sonrası frontend’e gösterilecek menü ve feature flag bilgilerini sağlamak
* Admin yetkisi gerektiren app settings veya integration yönetimini korumak
* JWT içindeki `roleId`, `userId`, `tenantId` gibi değerlerle menü filtrelemek

Örnek kullanım:

```text
frontend
  -> auth-service login
  -> access token alınır
  -> app-service /menus/by-role çağrılır
  -> roleIds içinde kullanıcının roleId değeri olan menüler döner
```

App-service, auth-service tablosuna foreign key vermemelidir. `userId`, `roleId` ve `tenantId` gibi değerler referans olarak kullanılmalıdır.

---

### 4.2 user-service

`user-service`, kullanıcı profili, roller, tenant/clinic ilişkileri ve profil bilgilerini yönetir.

App-service user-service’den sadece referans ID düzeyinde etkilenir.

Kullanım örnekleri:

* Feedback kaydında `userId` saklanır.
* Menü filtrelemede `roleId` kullanılır.
* Diyetisyen veya tenant özel entegrasyonlarda `ownerType = DIETITIAN` ve `ownerId = dietitianId` kullanılabilir.
* Kullanıcı silindiğinde feedback kayıtları korunabilir; ancak kişisel veri politikası gerekiyorsa anonimleştirme yapılabilir.

App-service kullanıcı detaylarını kopyalamamalıdır. Gerektiğinde user-service’den API ile okunmalıdır.

---

### 4.3 subscription-service

`subscription-service`, plan, abonelik, entitlement ve kullanım limitlerinden sorumludur.

App-service ile subscription-service arasındaki ilişki iki yönlü olabilir:

1. Subscription-service ödeme entegrasyonları için app-service’den provider bilgisi alabilir.
2. App-service bazı feature flag kontrollerinde subscription durumuna göre frontend davranışını etkileyebilir.

Örnek kullanım:

```text
subscription-service
  -> app-service: GetDefaultIntegration(type=PAYMENT, provider=IYZICO)
  -> secretRef ile ödeme provider credential bilgisi alınır
  -> checkout/payment işlemi yürütülür
```

App-service plan limiti hesaplamamalıdır. Plan, ödeme, fatura ve kullanım hakkı subscription-service içinde kalmalıdır.

---

### 4.4 notify-service

`notify-service`, SMS, email, push ve ileride WhatsApp bildirimlerinden sorumludur.

App-service, notify-service’e hangi provider’ın kullanılacağını söyler.

Örnek kullanım:

```text
notify-service
  -> app-service: GetDefaultIntegration(type=SMS, ownerType=SYSTEM)
  -> NETGSM entegrasyonu bulunur
  -> secretRef ile credential alınır
  -> SMS gönderilir
```

Email için:

```text
notify-service
  -> app-service: GetDefaultIntegration(type=EMAIL)
  -> AWS_SES veya SENDGRID provider bilgisi alınır
  -> email gönderilir
```

App-service mesaj göndermez. Sadece provider/config/secretRef bilgisini sağlar.

---

### 4.5 appointment-service

`appointment-service`, randevu ve takvim domain’inden sorumludur.

App-service bu servise şu noktalarda destek olur:

* Calendar integration feature flag
* Google Calendar entegrasyon bilgisi
* Online randevu UI feature flag’i
* Randevu modülü menü görünürlüğü
* Environment bazlı frontend route/config bilgisi

Örnek:

```text
appointment-service
  -> app-service: GetFeatureFlag("enable_google_calendar_sync")
  -> özellik açıksa Google Calendar senkronizasyonu çalıştırılır
```

---

### 4.6 chat-service

`chat-service`, mesajlaşma ve görüntülü görüşme domain’inden sorumludur.

App-service chat-service için şu bilgileri sağlayabilir:

* Yeni chat UI feature flag’i
* Video call provider entegrasyonu
* Chat menü görünürlüğü
* Environment bazlı socket base URL bilgisi

Örnek:

```text
web/mobile
  -> app-service: GetAppSettings(thefoodhero-mobile, PRODUCTION)
  -> chatSocketBaseUrl veya baseUrl bilgisi alınır
```

Eğer chat socket URL bilgileri app-service’de tutulacaksa `AppSettings` veya daha detaylı `config` alanı gerekebilir. Mevcut schema’da `AppSettings` içinde sadece `baseUrl` olduğu için detaylı endpoint/socket config için ileride `settings Json?` alanı eklenebilir.

---

### 4.7 ai-service

`ai-service`, öneri, analiz, duygu analizi, menü önerisi ve rapor üretimi gibi AI işlemlerinden sorumludur.

App-service ai-service için provider config kaynağı olabilir.

Örnek kullanım:

```text
ai-service
  -> app-service: GetDefaultIntegration(type=AI, provider=GEMINI veya CUSTOM)
  -> model, baseUrl, timeout gibi config alınır
  -> secretRef üzerinden API key okunur
  -> AI request yapılır
```

App-service AI işlemi yapmamalıdır. AI model seçimi, token hesaplama ve cevap üretimi ai-service içinde kalmalıdır.

---

### 4.8 geo-service

`geo-service`, konum bazlı diyetisyen eşleştirme ve harita/mesafe hesaplama işlerinden sorumludur.

App-service geo-service için map provider bilgisi sağlayabilir.

Örnek:

```text
geo-service
  -> app-service: GetDefaultIntegration(type=MAP, provider=GOOGLE)
  -> Google Maps config alınır
  -> secretRef ile API key alınır
```

---

### 4.9 store-service

`store-service`, diyetisyenlerin ürün/dijital satış modülünden sorumludur.

App-service store-service’e şu alanlarda destek olur:

* Payment provider lookup
* Storage provider lookup
* Store modülü feature flag
* Ürün satış modülü menü görünürlüğü
* Webhook endpoint config bilgisi

Örnek:

```text
store-service
  -> app-service: GetDefaultIntegration(type=PAYMENT, ownerType=DIETITIAN, ownerId=dietitianId)
  -> özel provider yoksa SYSTEM default provider alınır
```

---

### 4.10 web / mobile / admin frontend

Frontend uygulamaları app-service’i yoğun şekilde kullanır.

Kullanım örnekleri:

* Aktif menüleri getirme
* Role göre menü filtreleme
* App versiyon bilgisi alma
* Maintenance veya force update bilgisi alma
* Feature flag değerlerini okuma
* Feedback gönderme
* Environment bazlı base URL okuma
* Admin panelden app settings, menus, feature flags ve integrations yönetme

Frontend için sık kullanılan endpointler cache destekli olmalıdır.

## 6. Veritabanı Tasarımı

App-service kendi veritabanına sahip olmalıdır. PostgreSQL kullanımı uygundur. Diğer servislerin tablolarına foreign key verilmemelidir.

Ancak aynı app-service veritabanı içindeki modeller arasında relation kurulabilir.

Önerilen yaklaşım:

| İlişki | FK Verilmeli mi? | Açıklama |
|---|---:|---|
| `AppSettings.appId -> App.id` | Evet | Aynı servis boundary içinde. |
| `FeatureFlag.appId -> App.id` | Evet | Aynı servis boundary içinde. |
| `AppFeedback.userId -> user-service.User.id` | Hayır | Farklı servis boundary. |
| `AppMenu.roleIds -> user/auth role id` | Hayır | Farklı servis boundary. |
| `Integration.ownerId -> tenant/user/dietitian id` | Hayır | Polymorphic ve servisler arası referans. |

Mevcut schema MVP için kullanılabilir. Ancak üretim kalitesinde relation, index ve secret yönetimi güçlendirilmelidir.

### 8.7 Integration

`Integration`, dış sistem sağlayıcı tanımlarını tutar.

| Alan | Tip | Açıklama |
|---|---|---|
| id | String | Primary key |
| provider | IntegrationProvider | Sağlayıcı |
| type | IntegrationType | SMS, EMAIL, PAYMENT, STORAGE, MAP, AI, WEBHOOK |
| name | String | Entegrasyon adı |
| ownerType | IntegrationOwnerType | SYSTEM, MERCHANT, DIETITIAN, USER |
| ownerId | String? | Sahip ID |
| status | IntegrationStatus | ACTIVE, PASSIVE, ERROR, DISABLED |
| isDefault | Boolean | Varsayılan mı |
| config | Json? | Hassas olmayan config |
| secretRef | String? | Secret manager referansı |
| encryptedData | Json? | Şifrelenmiş credential |
| lastSuccessAt | DateTime? | Son başarılı işlem |
| lastErrorAt | DateTime? | Son hata zamanı |
| lastErrorMsg | String? | Son hata mesajı |
| createdAt | DateTime | Oluşturulma tarihi |
| updatedAt | DateTime | Güncellenme tarihi |

Bu model app-service’in en kritik modelidir.

Önemli kurallar:

* Secret bilgiler plaintext tutulmamalıdır.
* `config` sadece hassas olmayan değerler için kullanılmalıdır.
* API key, password, token, secret gibi değerler `secretRef` veya `encryptedData` üzerinden yönetilmelidir.
* `isDefault` için aynı owner/type altında tek default garanti edilmelidir.
* Hata mesajları sanitize edilmelidir.

## 9. Prisma Model Taslakları

Mevcut schema korunarak önerilen geliştirilmiş taslak aşağıdaki gibi olabilir:

```prisma
model App {
  id String @id @default(cuid())

  appName String @unique
  version String

  settings     AppSettings[]
  featureFlags FeatureFlag[]

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@map("App")
}

model AppSettings {
  id String @id @default(cuid())

  appId       String
  name        String
  appType     AppType
  environment Environment

  baseUrl String?
  version String?
  config  Json?

  maintenanceMode    Boolean @default(false)
  forceUpdateVersion String?
  minSupportedVersion String?

  isActive Boolean @default(true)

  app App @relation(fields: [appId], references: [id])

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([appId, environment])
  @@index([environment])
  @@index([appType])
  @@index([isActive])
  @@map("AppSettings")
}

model AppMenu {
  id String @id @default(cuid())

  appId      String?
  name       String
  parentName String?
  title      String
  icon       String
  url        String

  roleIds        String[] @default([])
```

## 10. Kritik İş Akışları

## 10.1 Uygulama Ayarı Okuma Akışı

```text
1. Frontend veya servis appName + environment bilgisiyle app-service'e istek atar.
2. App tablosundan appName ile uygulama bulunur.
3. AppSettings tablosundan appId + environment ile ayar kaydı alınır.
4. isActive false ise hata veya fallback response döner.
5. baseUrl, version, config, maintenance bilgileri response olarak döner.
6. Sonuç Redis cache'e yazılır.
```

Örnek endpoint:

```text
GET /app-settings/by-app/thefoodhero-web/PRODUCTION
```

Örnek response:

```json
{
  "appName": "thefoodhero-web",
  "environment": "PRODUCTION",
  "appType": "WEB",
  "baseUrl": "https://thefoodhero.com",
  "version": "1.0.0",
  "maintenanceMode": false,
  "config": {
    "apiBaseUrl": "https://api.thefoodhero.com",
    "chatSocketUrl": "https://api.thefoodhero.com/chat/socket.io"
  }
}
```

---

## 10.2 Rol Bazlı Menü Okuma Akışı

```text
1. Kullanıcı frontend'e giriş yapar.
2. auth-service access token üretir.
3. Frontend token içinden veya user endpointinden roleId bilgisini alır.
4. Frontend app-service /menus/by-role endpointini çağırır.
5. App-service isActive true olan ve roleIds içinde ilgili roleId bulunan menüleri getirir.
6. parentName ve orderIndex bilgilerine göre menü ağacı oluşturulur.
7. Menü listesi frontend'e döner.
```

Örnek endpoint:

```text
GET /menus/by-role/:roleId?appId=thefoodhero-web
```

Örnek Prisma filtre:

```ts
where: {
  isActive: true,
  roleIds: {
    has: roleId
  }
}
```

---

## 10.3 Feature Flag Kontrol Akışı

```text
1. Client veya servis feature key için app-service'e istek atar.
2. appId + environment + key ile FeatureFlag bulunur.
3. isActive false ise default davranış uygulanır.
4. valueType değerine göre value parse edilir.
5. Parse edilmiş değer response olarak döner.
```

Örnek endpoint:

```text
GET /feature-flags/:key?appId=xxx&environment=PRODUCTION
```

Örnek response:

```json
{
  "key": "enable_new_chat_ui",
  "value": true,
  "valueType": "BOOLEAN"
}
```

---

## 10.4 Feedback Oluşturma Akışı

```text
1. Kullanıcı uygulama içinden feedback formunu açar.
2. Yorum, screenshot ve context bilgisi gönderir.
3. app-service request'i validate eder.
4. Screenshot boyutu kontrol edilir.
5. Feedback PENDING status ile kaydedilir.
6. app.feedback.created eventi yayınlanır.
7. Admin panelde feedback listelenir.
```

Örnek endpoint:

```text
POST /feedback
```

Örnek request:

```json
{
  "comment": "Randevu takviminde tarih seçerken hata alıyorum.",
  "screenshotBase64": "...",
  "context": {
    "route": "/appointments",
    "browser": "Chrome",
    "appVersion": "1.0.0",
    "environment": "PRODUCTION"
  }
}
```

---

## 10.5 Feedback Durum Güncelleme Akışı

```text
1. Admin kullanıcı feedback detayını açar.
2. Status PENDING -> IN_PROGRESS yapılır.
3. Çözüm sonrası RESOLVED yapılır.
4. resolvedAt alanı güncellenir.
5. app.feedback.updated eventi yayınlanır.
```

Önerilen status akışı:

```text
PENDING -> IN_PROGRESS -> RESOLVED
PENDING -> REJECTED
IN_PROGRESS -> REJECTED
```

---

## 10.6 Bilgi Talep Formu Akışı

```text
1. Landing page üzerinde kullanıcı bilgi talep formunu doldurur.
2. app-service /info-requests endpointine request atılır.
3. Email, ad, soyad ve mesaj validate edilir.
4. AppInfoReq kaydı oluşturulur.
5. app.infoRequest.created eventi yayınlanır.
6. notify-service opsiyonel olarak admin'e email bildirimi gönderir.
7. Admin panelden talep CONTACTED veya CONVERTED yapılır.
```

Örnek endpoint:

```text
POST /info-requests
```

---

## 10.7 Default Integration Lookup Akışı

```text
1. Bir servis belirli integration type için provider bilgisine ihtiyaç duyar.
2. Önce owner özelinde ACTIVE + isDefault integration aranır.
3. Owner özelinde kayıt yoksa SYSTEM default aranır.
4. Integration bulunursa config ve secretRef döner.
5. Hassas data response içinde plaintext dönmez.
6. İlgili servis secretRef ile secret manager'dan credential okur.
```

Örnek:

```text
notify-service
  -> GET /internal/integrations/default?type=SMS&ownerType=SYSTEM
```

Fallback stratejisi:

```text
1. ownerType + ownerId + type + isDefault + ACTIVE
2. SYSTEM + type + isDefault + ACTIVE
3. Uygun kayıt yoksa hata
```

Örnek response:

```json
{
  "provider": "NETGSM",
  "type": "SMS",
  "name": "Default NetGSM SMS Provider",
  "config": {
    "header": "TFHERO"
  },
  "secretRef": "thefoodhero/prod/netgsm"
}
```

---

## 10.8 Integration Test Connection Akışı

```text
1. Admin panelden entegrasyon test edilir.
2. app-service ilgili provider için test strategy seçer.
3. SecretRef veya encryptedData ile credential resolve edilir.
4. Provider'a test request yapılır.
5. Başarılıysa lastSuccessAt güncellenir.
6. Başarısızsa status ERROR, lastErrorAt ve lastErrorMsg güncellenir.
7. app.integration.tested eventi yayınlanır.
```

Not:

App-service test connection yapabilir; ancak asıl SMS/email/payment operasyonlarını ilgili servisler yapmalıdır.

## 13. Cache Stratejisi

App-service verileri genellikle sık okunan ve az değişen verilerdir. Bu nedenle Redis cache kullanımı önemlidir.

Cache’e uygun veriler:

* App settings
* Feature flag listesi
* Tekil feature flag değeri
* Role göre menüler
* Default integration lookup sonucu

Önerilen Redis key yapısı:

```text
app:settings:{appName}:{environment}
app:feature-flags:{appName}:{environment}
app:feature-flag:{appName}:{environment}:{key}
app:menus:{appId}:{roleId}
app:integration:default:{type}:{ownerType}:{ownerId}
```

TTL önerisi:

```text
app settings: 15-60 dakika
feature flags: 5-15 dakika
menus: 15-60 dakika
integration lookup: 5-15 dakika
```

Cache invalidation kuralları:

* AppSettings güncellenince `app:settings:*` ilgili key temizlenir.
* FeatureFlag güncellenince ilgili app/environment flag keyleri temizlenir.
* AppMenu güncellenince ilgili app/role menü cache’i temizlenir.
* Integration güncellenince ilgili default integration cache’i temizlenir.
* Event publish sonrası consumer servisler kendi local cache’lerini temizleyebilir.

## 14. Transaction ve Idempotency

Aşağıdaki işlemler transaction içinde yapılmalıdır:

* App + AppSettings birlikte oluşturma
* Menü sıralama güncelleme
* Integration default değiştirme
* Integration status güncelleme
* Feedback status güncelleme
* Feature flag bulk update
* App settings update + cache invalidation event kaydı

Integration default değiştirme transaction içinde yapılmalıdır.

Örnek akış:

```text
1. Aynı type + ownerType + ownerId için mevcut default kayıtları false yapılır.
2. Seçilen integration isDefault true yapılır.
3. Event kaydı oluşturulur.
4. Cache invalidation yapılır.
```

Webhook tarzı external callback app-service’de sınırlı olacaktır. Ancak ileride integration provider callback kayıtları tutulacaksa idempotency için request ID veya provider event ID saklanmalıdır.

## 15. Güvenlik Tasarımı

App-service güvenlik açısından kritik bir servistir. Özellikle `Integration` modeli nedeniyle provider secret, API key ve credential yönetimi dolaylı olarak bu servise bağlıdır.

### 15.1 Endpoint Yetkilendirme

Endpointler üç seviyeye ayrılmalıdır:

```text
Public
Internal
Admin
```

Public endpointler:

* Feature flag okuma
* Aktif menü okuma
* Feedback oluşturma
* Info request oluşturma

Internal endpointler:

* Default integration lookup
* Internal app settings lookup
* Internal feature flag lookup
* Integration success/error güncelleme

Admin endpointler:

* App settings yönetimi
* Menü yönetimi
* Feature flag yönetimi
* Integration yönetimi
* Feedback durum yönetimi
* Info request durum yönetimi

### 15.2 Secret Yönetimi

Kurallar:

* Secret değerleri `config` içinde tutulmamalıdır.
* API key, token, private key ve password response içinde dönülmemelidir.
* `secretRef` admin dışı endpointlerde maskelenmelidir.
* `encryptedData` varsa AES-GCM gibi authenticated encryption kullanılmalıdır.
* Encryption key kod içinde veya repo içinde tutulmamalıdır.
* `lastErrorMsg` sanitize edilmelidir.
* Provider raw response loglanırken credential alanları maskelenmelidir.

### 15.3 Rate Limit

Rate limit önerilen endpointler:

```text
POST /feedback
POST /info-requests
GET  /feature-flags/public
POST /admin/integrations/:id/test
```

### 15.4 Audit Log

Admin tarafından yapılan kritik değişiklikler audit edilmelidir.

Audit edilmesi gereken işlemler:

* Integration oluşturma/güncelleme/silme
* Integration default değiştirme
* Feature flag güncelleme
* App settings güncelleme
* Menü güncelleme
* Feedback status değiştirme

İleride ayrı bir `audit-service` kurulana kadar app-service içinde `AppAuditLog` tablosu düşünülebilir.

## 16. Validasyon Kuralları

### 16.1 App

* `appName` boş olmamalıdır.
* `appName` unique olmalıdır.
* `version` boş olmamalıdır.
* Versiyon formatı semver standardına yakın olmalıdır.

Örnek:

```text
1.0.0
1.1.0-beta.1
```

---

### 16.2 AppSettings

* `appId` geçerli bir App kaydı olmalıdır.
* Aynı `appId + environment` tekrar oluşturulmamalıdır.
* `baseUrl` geçerli URL formatında olmalıdır.
* `config` valid JSON olmalıdır.
* `forceUpdateVersion` varsa semver formatında olmalıdır.
* `minSupportedVersion` varsa semver formatında olmalıdır.

---

### 16.3 AppMenu

* `name` boş olmamalıdır.
* `name` unique olmalıdır.
* `title` boş olmamalıdır.
* `url` geçerli route veya URL formatında olmalıdır.
* `roleIds` array olmalıdır.
* `orderIndex` integer olmalıdır.
* `parentName` varsa mevcut bir menüye karşılık gelmelidir.
* `icon` frontend icon setiyle uyumlu olmalıdır.

---

### 16.4 FeatureFlag

* `key` boş olmamalıdır.
* `key` standardize edilmelidir.
* `valueType = BOOLEAN` ise value sadece `true` veya `false` olmalıdır.
* `valueType = NUMBER` ise value sayıya çevrilebilmelidir.
* `valueType = JSON` ise value valid JSON olmalıdır.
* Aynı `appId + environment + key` tekrar oluşturulmamalıdır.
* `rolloutPercentage` varsa 0-100 arasında olmalıdır.

Önerilen key standardı:

```text
snake_case
```

Örnek:

```text
enable_ai_recommendation
enable_new_chat_ui
max_feedback_screenshot_size_mb
```

---

### 16.5 AppFeedback

* `comment` boş olmamalıdır.
* `comment` maksimum karakter sınırına sahip olmalıdır.
* `screenshotBase64` opsiyonel olmalıdır.
* Screenshot boyutu sınırlandırılmalıdır.
* `context` valid JSON olmalıdır.
* Kullanıcı başına rate limit uygulanmalıdır.

---

### 16.6 AppInfoReq

* `email` geçerli email formatında olmalıdır.
* `name` ve `surname` minimum 2 karakter olmalıdır.
* `message` maksimum karakter sınırına sahip olmalıdır.
* Spam koruması uygulanmalıdır.
* Aynı email’den kısa sürede çok sayıda kayıt engellenmelidir.

---

### 16.7 Integration

* `provider` zorunlu olmalıdır.
* `type` zorunlu olmalıdır.
* `name` boş olmamalıdır.
* `ownerType = SYSTEM` ise `ownerId` boş olabilir.
* `ownerType != SYSTEM` ise `ownerId` dolu olmalıdır.
* `isDefault = true` yapılırken aynı owner/type altında başka default olmamalıdır.
* `config` içinde secret alanlar olmamalıdır.
* `secretRef` varsa formatı doğrulanmalıdır.
* `status = ACTIVE` yapılmadan önce test connection opsiyonel olarak çalıştırılmalıdır.

## 20. Domain Servisleri

### 20.1 FeatureFlagParser

Feature flag değerini `valueType` değerine göre parse eder.

```ts
class FeatureFlagParser {
  parse(value: string, valueType: FeatureValueType) {
    switch (valueType) {
      case "BOOLEAN":
        return value === "true";
      case "NUMBER":
        return Number(value);
      case "JSON":
        return JSON.parse(value);
      case "STRING":
      default:
        return value;
    }
  }
}
```

## 25. Migration Stratejisi

Mevcut schema production’a çıkmadan önce düzenlenebilir. Eğer production’da kullanılmaya başlandıysa migration dikkatli yapılmalıdır.

Önerilen güvenli sıra:

```text
1. Nullable yeni alanları ekle.
2. Yeni indexleri ekle.
3. Duplicate veri kontrolü yap.
4. Backfill gerekiyorsa script çalıştır.
5. Relation eklenecekse önce eksik App kayıtlarını oluştur.
6. Unique constraint ekle.
7. Kod tarafını yeni alanları kullanacak şekilde güncelle.
8. Cache invalidation ve event yapısını ekle.
9. Eski alanlar kaldırılacaksa sonraki migration’a bırak.
```

Riskli değişiklikler:

| Değişiklik | Risk |
|---|---|
| AppMenu.name unique yapmak | Duplicate name varsa migration fail olur. |
| AppSettings.appId relation eklemek | Karşılığı olmayan appId varsa fail olur. |
| FeatureFlag.appId relation eklemek | Karşılığı olmayan appId varsa fail olur. |
| Integration default unique index | Birden fazla default varsa fail olur. |
| screenshotBase64 nullable yapmak | Düşük riskli. |

## 28. Sonuç

`app-service`, TheFoodHero ekosisteminde sadece birkaç uygulama ayarı tutan basit bir servis olarak düşünülmemelidir. Bu servis, platformun merkezi konfigürasyon ve entegrasyon registry servisi olarak tasarlanmalıdır.

Bu yaklaşımla TheFoodHero’da web, mobil, admin panel ve mikroservislerin çalışma davranışları merkezi olarak yönetilebilir. Feature flag sistemi sayesinde yeni özellikler kontrollü açılabilir. Menü sistemi sayesinde frontend rollere göre dinamik hale gelir. Integration modeli sayesinde SMS, email, ödeme, AI, harita ve storage sağlayıcıları sistem genelinde veya owner bazlı yönetilebilir.

MVP aşamasında temel yapı sade tutulmalıdır. App, AppSettings, AppMenu, FeatureFlag, Feedback, InfoRequest ve Integration modelleri yeterlidir. Ancak production kalitesinde cache, event publish, secret masking, admin authorization ve transaction yönetimi mutlaka eklenmelidir.

Bu yapı kurulduğunda app-service, TheFoodHero’nun ileride büyüyecek SaaS ekosistemi için merkezi ve sürdürülebilir bir platform konfigürasyon servisi haline gelir.
